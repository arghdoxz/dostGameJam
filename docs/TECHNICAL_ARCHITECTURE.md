# Technical Architecture

Godot 4.7.2, typed GDScript. Implemented in Prompt 2 (functional skeleton). Differences from the original plan:
- **Catalog injection:** core systems read definitions from `MatchState.catalog` (a `ContentCatalog`, RefCounted) instead of the `ContentDB` autoload. The autoload only builds the catalog for the UI. This keeps the core runnable headless and on a future server.
- **App root:** `scenes/boot/app.tscn` (`scripts/app.gd`) swaps screens and owns the single `MatchController`. Screens are thin `.tscn` roots whose scripts build their children in code.
- **Tests:** custom runner `tests/run_tests.gd` (no GUT). UI smoke test `tests/smoke_ui.gd`.
- **Content:** `.tres` files are generated by `tools/generate_content.gd` (rerun after changing its tables) and can also be edited in the Godot editor.
- **Presentation (Prompt 3):** the text `TownView`/`HandView`/`ReactionPrompt` were replaced by a tabletop of code-built components (below). There are still no per-component `.tscn` files; each screen is a thin scene root and components are `class_name` scripts.

## Prompt 3 additions
**Rules core**
- `MatchState.Resume.FINAL` and `TurnSystem.run_final_resolution`: outstanding forecasts resolve at the round cap before scoring (R6). `DisasterResolver._after_resolution` re-enters it after each Reaction window.
- `VictoryEvaluator.simultaneous_winners(players, durability_before)` takes a pre-blow durability snapshot taken in `DisasterResolver._resolve` (R8).
- Read-only helpers for the UI, so it never re-implements rules: `DamageCalculator.preview` (same `breakdown` as resolution), `ActionEnumerator.explain` (why a card cannot be used), `ContentCatalog.card_ids`.
- `MatchController`: `submit` refuses re-entrant calls, `abandon()` clears the match from any phase (signal `match_abandoned`), `has_match()`. `App` detaches the old screen before starting a match.

**UI components (`scripts/ui/`)** - all render from `MatchState` and emit signals; none mutate state.
| Component | Role |
|---|---|
| `MatchScreen` | Composes everything; builds `GameAction`s, tracks selection, target choice and queued summaries |
| `BoardView` | Table layout. `slots_for(state, actor)` seats the actor at the near edge (2: near/far; 3: near/left/right; 4: near/left/far/right) |
| `MapView` | Perspective map plane, one region per player (`REGION_SLOTS`), `BuildingToken`s, `ForecastMarker`s (no longer draws the last-played card) |
| `SeatView`, `BackFan` | Player mat: portrait, RP bar and number, status text, counts, face-down hand fan |
| `HandFan`, `CardView` | Fanned hand with hover/selection lift; layered card (art, frame, text) or card back |
| `ActionPanel` | Selected card text, per-target damage preview, one button per legal action, the reason when none |
| `PaymentPicker`, `DiscardDialog`, `ConfirmDialog` | Modals built on `ModalPanel` |
| `DisasterPanel`, `ResolutionSummary` | Reaction window breakdown and the "what happened" list |
| `DeckPile`, `TurnHeader`, `EventLog`, `PassDeviceScreen` | Decks, header/phase hint, log, hot-seat cover |
| `DamageText`, `EventText`, `CardText` | Pure text formatting (numbers come from the rules core) |
| `AssetLibrary`, `UiTheme` | The only asset-path code; theme fonts and label variants |

**Tools:** `tools/generate_asset_manifest.gd`, `tools/capture_screens.gd`.

## Prompt 4 additions
**Tutorial (`scripts/tutorial/`)** - an interactive lesson on top of a normal match; it adds no rules.
| File | Role |
|---|---|
| `TutorialScenario` | Fixed seats (Ana/Coastal, Ben/Upland), seed 4242, and `arrange(state)`, which only *moves* cards between decks and hands to stack both hands. Passed to `MatchController.start(..., prepare)` so the controller still owns the state. |
| `TutorialStep`, `TutorialContext` | A step has title, body, success line, highlight key(s) and a completion predicate over the context (state, events since the step began, selected card, chosen target, whether the cover or summary is up). INFO steps use a Next button; ACTION steps always offer Skip step. |
| `TutorialScript` | `build()` returns the 32 steps. |
| `TutorialCoach` | A Control at z 400 (above the pass-device cover at 300 and modals at 200) added as a child of the match screen only by `App.start_tutorial()`. Draws the instruction panel (placed to avoid the highlighted area) and pulsing outlines, overrides its text while the hot-seat cover or a summary is showing, and emits `exit_requested`, `restart_requested`, `start_match_requested`. |

`MatchScreen.highlight_rects(key)` and `tutorial_info()` expose where things are on screen; `HandFan.card_rect`, `BoardView.pile`, `TurnHeader.end_turn_button/log_button` and `PassDeviceScreen.ready_button` exist for the same reason. `LastPlayView` (top-left of the table) replaced the card that used to sit in the map centre (BUG-005).

**QA driver (`tools/qa_driver.gd`)** - a SceneTree script that boots the real `App` scene in a window and plays it with `Input.parse_input_event` at pixel positions (`root.get_final_transform() * canvas_position`; motion, press, release with frame waits in between). Commands: click by button text, card, pile, seat, region or coordinates; hover; key; type; wait; shot; dump (what a player can see); audit (screen versus state); resize; caption; `auto` (heuristic player, still by clicks); `debug_*` (bypass the rules; any run using them is "debug-assisted"). Modes: interactive (`--io <dir>`, a command file polled each frame), replay (`--script <file>`), or recording (`tools/record_demo.ps1` adds Godot Movie Maker). Never calls `MatchController.submit` for player-facing commands.

**Hot-seat privacy rule (existing, relied on by the tutorial):** `PassDeviceScreen` is shown whenever the acting player changes, including reactions.

**Tools:** `tools/qa_driver.gd`, `tools/record_demo.ps1`.

## Principles
- The rules core is pure `RefCounted` code with no Node or UI references, so it can be unit tested headless and later driven over a network.
- Static data (definitions) is separate from runtime state.
- All player input becomes a serializable `GameAction`. The UI never edits state directly.
- No networking code is written now.

## Layers
```
UI (scenes)  --GameAction-->  MatchController (Node)  -->  RulesEngine (RefCounted)
     ^                              |                           |
     +------ events_emitted --------+<------ GameEvent[] -------+
```

### Rules core: `scripts/core/`
- **State:** `MatchState`, `PlayerState`, `CardInstance` (uid + definition id), `BuildingInstance`, `PendingDisaster` (a Forecast). `MatchState` holds a seeded `RandomNumberGenerator` so matches replay deterministically.
- **Actions:** `GameAction` base plus `DrawAction`, `PlayCardAction`, `ReactAction`, `PassReactionAction`, `EndTurnAction`. Each has `to_dict()` / `from_dict()` and carries only ids.
- **Engine:** `RulesEngine.validate(state, action) -> ValidationResult` (ok flag and reason) and `RulesEngine.apply(state, action) -> Array[GameEvent]`. `apply` is only called after a successful `validate`.
- **Systems:** `TurnSystem`, `DeckSystem`, `DisasterResolver`, `DamageCalculator`, `VictoryEvaluator`.
- **Events:** `GameEvent` (type + dictionary payload), e.g. card_drawn, card_played, forecast_placed, reaction_window_opened, damage_dealt, building_destroyed, player_eliminated, game_over.

### Definitions: `scripts/defs/`, data in `content/`
- `CardDefinition` (id, display_name, type, cost, tags, flavor, dr_tip, art_id), subclassed as `ResourceCardDef`, `BuildingCardDef`, `PreparednessCardDef`, `DisasterCardDef`.
- `DisasterDefinition` (id, level, damage_min/max, targeting mode, tags, secondary effects). `DisasterCardDef` points to one.
- `BuildingDefinition` (reduction per tag, durability, cost).
- `EffectDefinition`: a small closed set (DamageReduction, Heal, Repair, Draw, ExtraPlay, Reserve) interpreted by the engine. No scripts in data.
- `TerritoryDefinition`, `MatchConfig` (starting RP, hand size, hand limit, round cap, plays per turn).
- `ContentRegistry.tres` lists every definition explicitly because directory scanning is unreliable in exports.
- `ContentDB` autoload: the only autoload in the MVP. It loads the registry and answers lookups by id.

### Presentation: `scenes/`, `scripts/ui/`
- `MatchController` (Node) owns the engine, accepts actions, emits `events_emitted(events)` and `state_changed`.
- **Scene flow:** `Boot -> MainMenu -> MatchSetup -> Match -> GameOver`.
- `Match` contains `BoardView` (seats, `MapView`, `DeckPile` x2), `HandFan`, `ActionPanel`, `DisasterPanel`, `ResolutionSummary`, dialogs, `PassDeviceScreen`, `EventLog`, `DebugPanel` (see "Prompt 3 additions").
- Look: a 2D board with a pseudo-3D feel (isometric tiles, drop shadows, card tilt and hover). No 3D nodes.
- `AssetLibrary` resolves an art id to a texture and falls back to a placeholder.

### Debug: `scripts/debug/`
`DebugPanel` (F1): set seed, give card, set RP, force a disaster, export the action log.

## Networking boundary (future, not built)
A networked controller can replace `MatchController` and relay the same serialized `GameAction`s to an authoritative engine. Requirements already met by this design: deterministic seeded engine, serializable actions and events, no UI references in the core. Hidden-information filtering of state per player is the networking developer's job.

## Naming
- Files and folders: `snake_case`. Classes (`class_name`): `PascalCase`.
- Content ids: prefixed by kind, e.g. `res_materials`, `bld_seawall`, `disaster_flood`, `prep_go_bag`. The content file is named after its id.
- Art files: `<category>_<id>.png`, e.g. `card_disaster_flood.png`.
- Signals: past-tense `snake_case`. Constants: `UPPER_SNAKE`.
